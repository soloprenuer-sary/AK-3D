# Secure customer 3D-file storage and in-browser 3D model viewing for WordPress/WooCommerce

Research date: 2026-11-11. Notes compiled from official docs where fetched; secondary sources are flagged. Items marked "(general knowledge, unverified)" appear only under Inferences and were not confirmed by a fetched source.

## 1. Secure storage design for customer uploads (location, validation, chunking, object storage, scanning, access, retention, cost)

### Takeaway
Best fit for a solo developer on budget hosting: accept the upload in the browser, send it straight to an S3-compatible bucket (Cloudflare R2 or Backblaze B2) using short-lived presigned multipart URLs issued by an authenticated WordPress REST route, keep the bucket private, and serve files to admin/owner only through freshly signed expiring GET URLs. This sidesteps PHP/nginx/Cloudflare-proxy size limits, keeps customer files off the web root and out of WP media, and costs almost nothing at expected volumes (R2 free tier is 10 GB; B2 is $6.95/TB-month). If staying on-server, use a non-public directory with server-generated random names, extension AND content checks, and X-Accel-Redirect / X-Sendfile for download.

### Cited Findings

**OWASP baseline (file upload)**
- OWASP: allowlist only business-needed extensions, validate the extension after decoding the filename, reject double extensions, null bytes, case tricks, server-mapped alternates (.phtml etc.) and filenames containing colons; treat blocklists as weak — [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
- Client-supplied Content-Type is easily spoofed (use only as a quick allowlist check); verify magic bytes/file signature alongside it, but do not rely on signature alone — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
- Replace user filenames with a server-generated random string (UUID/GUID); if originals must be kept, cap length and restrict to a safe character set — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
- Storage preference order: different host (best) > outside webroot > inside webroot only as last resort, write-only with access controls on reads; map files through a handler (ID to filename) rather than exposing stored names; disable per-directory config overrides (.htaccess/web.config) in upload dirs — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
- Set upload size limits; measure archive size after decompression; apply least-privilege filesystem permissions; scan with antivirus/sandbox; avoid ZIP uploads where possible; require authenticated users, check authorization to access files, protect against CSRF — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
- Images: decode and re-encode to an allowed format to strip metadata, with resource-limited, up-to-date libraries — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

**WordPress MIME handling (STL/STEP/3MF)**
- `upload_mimes` filter: `apply_filters('upload_mimes', $t, $user)` returns an array of allowed MIME types indexed by a regex of extensions; used to add or `unset()` types — [WP Developer Reference: upload_mimes](https://developer.wordpress.org/reference/hooks/upload_mimes/)
- `wp_check_filetype_and_ext()` starts from extension-to-MIME mapping against `get_allowed_mime_types()`; if the extension is not in the allowed list both `ext` and `type` come back false. For non-image files it runs PHP `finfo_file()`; generic binaries (`application/octet-stream`, `application/zip`) are accepted only when the claimed major type is application/video/audio; text types have their own allowlists; anything else must match exactly. Filter `wp_check_filetype_and_ext` receives the detected `$real_mime` (since 5.1.0) — [WP Developer Reference: wp_check_filetype_and_ext](https://developer.wordpress.org/reference/functions/wp_check_filetype_and_ext/)
- The reference page does not mention STL/STEP/3MF; the behaviour for them is inferred from the code description (see Inferences).

**WooCommerce's own protection**
- WooCommerce adds an `.htaccess` to `woocommerce_uploads` to block direct URL access to downloadable files; nginx ignores `.htaccess`. Protection depends on the download method (Force Downloads default; X-Accel-Redirect/X-Sendfile; Redirect only) — [WooCommerce docs: nginx protect uploads](https://developer.woocommerce.com/docs/code-snippets/using_nginx_server_to_protect_your_uploads_directory/)
- For nginx with Force Downloads / X-Accel-Redirect, add `location ~* /woocommerce_uploads/ { internal; }` before any regex static-file location (e.g. one matching .pdf/.zip). For "Redirect only" mode the doc says nginx cannot block direct access (only `autoindex off`) — [WooCommerce docs](https://developer.woocommerce.com/docs/code-snippets/using_nginx_server_to_protect_your_uploads_directory/)
- nginx `internal` locations return 404 to external requests but are reachable via `X-Accel-Redirect` response headers from the upstream; max 10 internal redirects — [nginx core module docs](https://nginx.org/en/docs/http/ngx_http_core_module.html)
- WooCommerce's own Product Add-Ons hardening doc warns that merely disabling directory listing only stops folder browsing; anyone with an exact file URL can still open it, so "don't use add-on uploads to store confidential documents" — [WooCommerce: Hardening File Uploads](https://woocommerce.com/document/product-add-ons/hardening-file-uploads/)
- A Plesk forum thread reports the woocommerce_uploads restriction can fail when Apache proxies to nginx; test direct URL after config changes — [Plesk forum thread](https://talk.plesk.com/threads/bug-plesk-nginx-proxy-stripping-performance-headers-cpu-spikes-on-all-woocommerce-downloads.394657/) (forum report, single source)

**Apache / LiteSpeed streaming offload**
- Apache `mod_xsendfile`: serves the file named in an `X-Sendfile` header; enable with `XSendFile On` and allow paths outside the request directory via `XSendFilePath` — [mod_xsendfile docs (tn123.org)](https://tn123.org/mod_xsendfile/); [Jadu docs](https://docs.jadu.net/central/developer/maintaining/files/x-send-file)
- LiteSpeed uses a URI (under the vhost docroot/context) in `X-LiteSpeed-Location`, not a filesystem path — [LiteSpeed docs](https://docs.litespeedtech.com/lsws/redirect/). A WordPress.org forum thread reports WooCommerce has no support for X-LiteSpeed-Location — [WP.org support thread](https://wordpress.org/support/?p=18989799) (forum report; verify)

**Chunked/resumable uploads**
- WordPress's default uploader often sends one monolithic POST and runs into `upload_max_filesize`/`max_execution_time`; a core Trac ticket proposes forcing a 1024KB `chunk_size` via the plupload params filter, still open as an enhancement (not shipped) — [WP Trac #64411](https://core.trac.wordpress.org/ticket/64411)
- Plupload pitfall: in Drupal's integration, chunk_size defaulted to PHP `post_max_size`, so chunking never kicked in when that was high; small-file edge cases with chunk_size have been reported; Big File Uploads plugin says chunk size must be below the PHP max — [Drupal Plupload issue](https://www.drupal.org/project/plupload/issues/2420749); [Plupload chunk docs ref](https://plupload.com/docs/v2/Options#chunk_size)
- tus protocol: `ankitpokhrel/tus-php` is a framework-agnostic pure-PHP tus v1.0.0 server/client (Composer; storage backends redis/file/apcu), works with tus-js-client and Uppy; example chunk size 5 MB. No WordPress-specific guidance found; one fork is marked abandoned — [tus-php fork listing](https://github.com/Inflection-Points/tus-php); [tus-php project page](https://awesome.ecosyste.ms/projects/github.com%2Fankitpokhrel%2Ftus-php)

**Direct-to-object-storage (Cloudflare R2)**
- R2 presigned URLs support GET, HEAD, PUT and DELETE (not POST form uploads); expiry 1 second to 7 days; signed server-side with AWS SigV4 using R2 API credentials (the Workers binding cannot generate them); work only on the S3 API domain `<ACCOUNT_ID>.r2.cloudflarestorage.com`, not custom domains; CORS needed for browser use; treat each URL as a bearer token (reusable until expiry); signature binds object, operation and expiry; including Content-Type when signing restricts upload type — [R2 presigned URLs docs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)
- R2 limits: max object 5 TiB via multipart (up to 10,000 parts); single PUT max 5 GiB (best under ~100 MB); part size min 5 MiB (except last) and max 5 GiB, parts equal size except last; incomplete multipart uploads auto-aborted after 7 days by default (configurable lifecycle) — [R2 multipart docs](https://developers.cloudflare.com/r2/objects/multipart-objects/)
- R2 supports a location hint including `apac`; hint applies only on first bucket creation; jurisdictions (eu, fedramp) are separate and no India/APAC jurisdiction is documented; Cloudflare's Snowflake guidance maps `apac` to Mumbai (AWS ap-south-1) for latency, not a residency guarantee — [R2 data location docs](https://developers.cloudflare.com/r2/reference/data-location/)

**Object storage pricing**
- R2 Standard: free 10 GB-month storage, 1M Class A ops, 10M Class B ops per month; paid $0.015/GB-month, $4.50/M Class A, $0.36/M Class B; egress free; free tier is Standard only; DeleteObject/AbortMultipartUpload free; usage rounded up to billing unit — [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- Backblaze B2: $6.95/TB-month (byte-hour billing), first 10 GB free, egress free up to 3x average monthly stored data then $0.01/GB, free egress via partner CDNs including Cloudflare and bunny.net; Class A/B/C calls free, Class D $0.004 per 10k (first 2,500/day free); no minimum file size or minimum retention fee — [Backblaze B2 pricing](https://www.backblaze.com/cloud-storage/pricing). The pricing page does not list regions.
- Secondary source claim (not verified against Backblaze): storage went from $6 to $6.95/TB on 1 May 2026; Wasabi $7.99/TB with 90-day minimum retention; R2 compared at $15/TB-month — [Upstash B2 pricing explainer](https://upstash.com/blog/backblaze-b2-pricing-explained-2026). Note R2's own page says $0.015/GB = ~$15/TB, consistent.
- AWS S3 Mumbai (ap-south-1) prices from vendor blogs conflict (about ₹1.73 to ₹2.10/GB-month, or ~$0.025/GB; egress after the first 100 GB roughly ₹8-9/GB) and are not official — [Precision Tech](https://precisiontech.in/cloud/amazon-aws-cloud/aws-pricing/aws-pricing-in-newdelhi/); [Cyfuture](https://cyfuture.cloud/kb/storage/cloud-storage-pricing-in-india-from-top-providers-in-2025). Treat as unverified.

**Malware scanning**
- ClamAV official minimum recommended RAM is 3 GiB+ for clamscan/clamd with the standard signature DB; ClamAV's team says devices under 1 GB will likely have problems loading signatures; clamd's signature reload can double memory use unless `ConcurrentDatabaseReload no` is set; a user report says 2 GB RAM plus ~1 GB swap works — [ClamAV docs](https://docs.clamav.net/print.html); [ClamAV blog](https://blog.clamav.net/2021/03/clamav-cvds-cdiffs-and-magic-behind.html); [Proxmox forum report](https://forum.proxmox.com/goto/post?id=342214)

### Inferences
- Because WordPress does not know STL/3MF/STEP/OBJ, `.stl` etc. will be rejected by the default check; adding them via `upload_mimes` is not sufficient on its own for binary types because `finfo` usually reports `application/octet-stream` (general knowledge, unverified for specific files), which passes only under the "application" major-type rule. Safer design: do NOT push customer CAD files through the media library at all. Use a custom REST/AJAX endpoint (or direct-to-bucket upload) with own validation, so no global `upload_mimes` widening exposes the whole site.
- Magic-byte checks worth implementing (general knowledge, unverified; confirm against format specs): 3MF = ZIP (`PK\x03\x04`) containing `3D/3dmodel.model`; ASCII STL starts with `solid`, binary STL has an 80-byte header plus a uint32 triangle count where file size must equal `84 + 50*count`; STEP begins with `ISO-10303-21;`; IGES has fixed-column 80-char records; OBJ is text (`v `, `f ` lines); images by their normal signatures. The binary-STL size equation is a strong cheap validator. ZIP-based 3MF needs decompressed-size and entry-count caps (OWASP warns about archives).
- With a direct-to-R2/B2 flow, the PHP server never touches the bytes, so magic-byte and malware checks must run after upload: either a small background job that fetches the first few KB (HTTP Range) for signature checks, or defer to the worker/admin download step. For 3D print files, real-world risk is mainly (a) disguised executables/scripts, (b) zip bombs inside 3MF, (c) malicious parser input hitting the admin's CAD/slicer software, so ClamAV adds limited value; a cheaper layer is size/signature/structure validation plus quarantine-until-validated state. On a 1 GB shared host ClamAV is impractical per the sources above; alternatives are a cloud scan (e.g., VirusTotal, general knowledge, unverified here) or skipping AV and relying on structural validation.
- Approximate monthly costs at 100 GB retained (assumes about ₹85-90 per US dollar, an assumption not sourced): R2 about 90 GB billable x $0.015 = ~$1.35; B2 about 90 GB x $0.00695 = ~$0.63. Either is a few hundred rupees per year; storage is a negligible part of the ₹15,000 budget. Free egress on both (R2 unconditional; B2 up to 3x stored) covers admin downloads.
- Recommended access model: bucket private; WordPress mints a presigned GET (short expiry such as 5-15 minutes) only after checking `current_user_can('manage_woocommerce')` or `get_current_user_id() === order owner`; never store signed URLs. Presigned URLs are bearer tokens (R2 docs), so keep expiry short and do not log them. Because presigned URLs cannot use custom domains on R2, files are fetched from the `r2.cloudflarestorage.com` host; for a custom domain you would need Workers or a Pro-plan WAF HMAC rule (R2 docs mention WAF HMAC requires Pro).
- Cloudflare's own docs say Free-plan proxied requests cap at 100 MB (see Q2); a direct browser-to-bucket PUT/multipart to the R2 S3 endpoint is not a request to the proxied WordPress zone, so it avoids that cap (inference from the documented limit applying to "incoming requests to proxied domains"; confirm by testing).
- Encryption at rest: R2 and B2 document their own server-side encryption (general knowledge, unverified in these notes); client-side/envelope encryption is rarely worth it at this scale. Backups: exclude the bucket from site backups or keep bucket versioning/lifecycle rules, because plugin backups that include a local uploads folder will copy customer designs into third-party storage.

### Gaps
- No verified current official pricing for AWS S3 Mumbai, Oracle OCI, E2E Networks, or other India-resident object stores; vendor blogs conflict.
- Backblaze region list and whether any Asia region exists were not confirmed (pricing page does not list regions).

- No WordPress-specific tus integration guide found; tus-php is not WordPress-native.

## 2. Hosting-level constraints (nginx, PHP, Cloudflare, timeouts, memory)

### Takeaway
Cloudflare Free caps proxied request bodies at 100 MB, nginx defaults to 1 MB, and PHP's defaults are also small, so 100-300 MB single-request uploads will fail on most budget stacks. The practical bypass is to upload directly to object storage (not through the proxied WordPress hostname) or to chunk into sub-100 MB requests.

### Cited Findings
- Cloudflare incoming request body limits for proxied domains: Free 100 MB, Pro 100 MB, Business 200 MB, Enterprise up to 5 GB (adjustable via zone Network > Maximum Upload Size); exceeding returns 413. Documented alternatives: split uploads into smaller requests, switch the DNS record to DNS-only, or upgrade the plan — [Cloudflare error 413 docs](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-413/)
- nginx `client_max_body_size` default 1m, 413 when exceeded, 0 disables the check, can be set per location (e.g. `/upload/ { client_max_body_size 50m; }`) — [nginx core docs](https://nginx.org/en/docs/http/ngx_http_core_module.html)
- nginx `client_body_timeout` default 60s, applied between two successive reads (not whole body); 408 on timeout. `client_body_temp_path` is where request bodies are buffered — [nginx core docs](https://nginx.org/en/docs/http/ngx_http_core_module.html)
- WordPress's uploader often sends a monolithic POST that hits `upload_max_filesize`/`max_execution_time` — [WP Trac #64411](https://core.trac.wordpress.org/ticket/64411)
- Chunk size must be below the PHP maximum, per a WordPress chunk-upload plugin's guidance, and Plupload chunk size fell back to `post_max_size` in one CMS integration — [Drupal Plupload issue](https://www.drupal.org/project/plupload/issues/2420749)
- R2 multipart: 5 MiB minimum part, 10,000 parts max; 100-300 MB at 8-16 MiB parts is roughly 7-40 parts — [R2 multipart docs](https://developers.cloudflare.com/r2/objects/multipart-objects/) (part math is an inference)

### Inferences
- Direct-to-bucket is the only approach that avoids all three limits at once (Cloudflare 100 MB, PHP `post_max_size`/`upload_max_filesize`/`max_execution_time`, nginx `client_max_body_size`/timeouts), and the PHP process uses essentially no memory or time on file bytes. WordPress only signs URLs and records metadata, a few KB per request.
- If staying server-side on shared hosting, chunks of about 5-10 MB (under 100 MB, under typical `upload_max_filesize` of 32-64 MB) avoid 413s; per-chunk requests also fit shorter timeouts. Hosts like shared cPanel setups usually do not expose nginx config (general knowledge, unverified); the PHP values can often be set through `.user.ini` or the host panel. A DNS-only "grey cloud" subdomain (e.g. `upload.example.com`) bypasses Cloudflare's proxy limit per the 413 doc, but exposes the origin IP and loses WAF/DDoS protection on that hostname.
- Keep the buckets, signing credentials and any HMAC secrets in `wp-config.php` constants or environment, not in the database.

### Gaps
- Typical PHP defaults (upload_max_filesize, post_max_size, max_execution_time, memory_limit) and how `.user.ini`/LiteSpeed handle them on specific budget hosts were not looked up.
- Which hosting provider/stack (Apache vs nginx vs LiteSpeed) the Akrinity site will use is unknown, which determines whether the X-Accel-Redirect or X-Sendfile route is available.

## 3. WordPress security hardening for uploads (PHP execution, nonces/capabilities, REST permission callbacks, rate limiting, bot protection, plugin vulnerabilities)

### Takeaway
Upload-related plugin vulnerabilities are a leading real-world takeover path, so the safest pattern is a small, purpose-built endpoint with strict capability/ownership checks, no files in executable directories, and Turnstile in front of any anonymous upload form. Prefer few plugins and your own code for the upload path.

### Cited Findings
- Patchstack's "State of WordPress Security in 2026" (secondary coverage): 11,334 new vulnerabilities in 2025 (+42%), about 91% in plugins; 46% of vulnerabilities unpatched at disclosure; median time to first mass exploitation reported as 5 hours — [Patchstack whitepaper page](https://patchstack.com/whitepaper/state-of-wordpress-security-in-2026/) (headline 46% figure seen on Patchstack's own page); [swif.ai summary](https://www.swif.ai/blog/wordpress-security-statistics) and other secondary sources for 91%/5-hour figures. Core vulnerability counts differ between secondary sources (2 vs 6).
- 2026 arbitrary-file-upload advisories exist across many plugins/themes, e.g. WP User Frontend <= 4.2.8 (fixed 4.2.9), Photo Engine <= 6.4.9 (fixed 6.5.0), Templatiq <= 0.2.5 (CVSS 9.9, no patch at time of entry), Webenvo theme <= 0.0.6 (CVSS 9.9), WooCommerce License Manager <= 7.0.6 (CVE-2026-28114, web shell upload) — [Patchstack database: WP User Frontend](https://patchstack.com/database/wordpress/plugin/wp-user-frontend/vulnerability/wordpress-user-frontend-ai-powered-frontend-posting-user-directory-profile-membership-user-registration-plugin-4-2-8-authenticated-author-arbitrary-file-upload-vulnerability); [Templatiq](https://patchstack.com/database/wordpress/plugin/templatiq/vulnerability/wordpress-templatiq-plugin-0-2-5-arbitrary-file-upload-vulnerability); [Patchstack tag page](https://patchstack.com/tag/arbitrary-file-upload)
- Wordfence reported an authenticated arbitrary file upload in Slider Revolution 7 (7.0.0-7.0.10) due to insufficient file type validation, patched in 7.0.11 on 4 May 2026 — [Wordfence blog](https://www.wordfence.com/blog/2026/05/authenticated-arbitrary-file-upload-vulnerability-patched-in-slider-revolution-7-wordpress-plugin/)
- Patchstack notes arbitrary-file-upload bugs let attackers upload backdoors that execute and give further access, and that this class is used in mass-exploit campaigns — [Patchstack: Templatiq entry](https://patchstack.com/database/wordpress/plugin/templatiq/vulnerability/wordpress-templatiq-plugin-0-2-5-arbitrary-file-upload-vulnerability); [WpStream entry](https://patchstack.com/database/wordpress/plugin/wpstream/vulnerability/wordpress-wpstream-plugin-4-11-2-arbitrary-file-upload-vulnerability)
- Blocking PHP execution in uploads on nginx: a case-insensitive regex location matching `.php` under `/wp-content/uploads/` with `deny all`, placed before the generic PHP handler (first regex match wins); do not block PHP across all of `wp-content` (breaks plugins/themes); Apache equivalent is a `.htaccess` FilesMatch with `Require all denied` in uploads if the host allows folder-level rules; test that a PHP file in uploads is actually blocked — [WPBeginner](https://www.wpbeginner.com/wp-tutorials/how-to-disable-php-execution-in-certain-wordpress-directories/); [MalCare](https://www.malcare.com/blog/disable-php-execution-directory-browsing/); [GetPageSpeed nginx WordPress recipe](https://nginx-wiki.getpagespeed.com/config/recipes/wordpress/) (community sources, not official docs)
- WordPress Developer Handbook security guidance: validate and sanitize all input ("validation/rejection is better" than sanitizing), escape output as late as possible, keep plugins/themes updated; the page fetched did not cover nonces/capabilities — [WP Developer: Security](https://developer.wordpress.org/apis/security/)
- Cloudflare Turnstile Free plan: free, unlimited verifications, up to 20 widgets per account, 10 hostnames per widget, 7-day analytics lookback, WCAG 2.2 AAA; excludes any-hostname widgets and branding removal — [Turnstile plans](https://developers.cloudflare.com/turnstile/plans/). Turnstile states it processes only data strictly necessary for the security function and does not access/store form entries — [Turnstile docs](https://developers.cloudflare.com/turnstile/)

### Inferences
- Design checklist for the upload endpoint (general WordPress practice, not fetched in this session; verify against the REST/Plugin handbook): register routes with `register_rest_route()` and a real `permission_callback` (never `__return_true` for upload routes); require login (WooCommerce customer) and verify `X-WP-Nonce` for cookie-authenticated requests; scope every file to an owner (user ID or order ID) and check ownership on every read, delete and sign request; sanitize filenames and never use client names on disk or as object keys; return opaque IDs; use `wp_generate_password()`/`random_bytes()` for keys.
- Rate limiting: Cloudflare WAF rate-limiting rules on the Free plan are limited (general knowledge, unverified); alternatively implement a per-user/IP transient counter (for example, N signing requests per hour) in the signing endpoint, plus a cap on total pending bytes per customer.
- Bot protection: put Turnstile on the guest-quote/upload form and verify the token server-side (siteverify) before issuing any presigned URL; for logged-in customers, per-user quotas matter more than CAPTCHA. Turnstile is free with no verification cap, so it is the cheaper choice compared with hCaptcha for this budget (hCaptcha pricing not researched).
- Common failure modes across the 2026 advisories: authenticated low-privilege users (Author/Subscriber) uploading arbitrary types, missing extension validation, and unauthenticated upload actions. All are avoided by an allowlist and a custom endpoint instead of a generic "upload anywhere" plugin. Keep plugin count low and enable auto-updates for security patches given reported mass-exploitation timelines.
- Defence in depth: even with the bucket approach, still block PHP execution under `/wp-content/uploads/` as a backstop.

- The Patchstack whitepaper itself was not read in full (gated); 91% and 5-hour statistics come from secondary coverage.

## 4. Privacy/IP protection practices (NDA/IP terms, T&Cs, watermarking, no reuse, consent for international phase)

### Takeaway
Little prescriptive authoritative guidance on 3D-print-shop IP terms was found; what can be sourced is India's DPDP framework timeline and notice content. Treat the T&C language and watermarking points below as practitioner suggestions to be reviewed by a lawyer, not sourced facts.

### Cited Findings
- India's DPDP Rules 2025 were notified in November 2025 with phased commencement: Board/Tribunal provisions immediate (13 Nov 2025); consent-manager provisions about one year later (reported as 14 Nov 2026); substantive duties (notice, consent, security safeguards, breach reporting) about 18 months later (reported as 13 or 14 May 2027, sources differ by a day) — [AZB & Partners](https://www.azbpartners.com/bank/update-indias-digital-personal-data-protection-framework-comes-into-effect/); [Mondaq summary](https://www.mondaq.com/india/privacy-protection/1708314/update-indias-digital-personal-data-protection-framework-comes-into-effect); [SCC Online](https://www.scconline.com/blog/post/2025/12/26/digital-personal-data-protection-rules-2025-key-highlights/); [Deccan Herald](https://www.deccanherald.com/amp/story/india%2Fcentre-notifies-dpdp-rules-implementation-planned-in-phases-spread-over-12-18-months-3798465)
- Notice requirements under the Rules (per secondary sources): self-contained, describing personal data collected and purpose, explaining how to withdraw consent and complain to the Board; available in English or any of the 22 Eighth Schedule languages; detailed breach intimation to the Board within 72 hours — [AZB & Partners](https://www.azbpartners.com/bank/update-indias-digital-personal-data-protection-framework-comes-into-effect/); [Mondaq](https://www.mondaq.com/india/privacy-protection/1722126/behind-the-buzzwords-real-world-implications-of-indias-dpdp-law)
- Cloudflare Turnstile states it does not access/store form entries, which helps when describing third parties in a privacy notice — [Turnstile docs](https://developers.cloudflare.com/turnstile/)
- OWASP recommends requiring authenticated users and authorization checks for file access, and isolating uploads from the web root, which supports a "your files are only visible to you and our team" promise — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

### Inferences
- Suggested T&C/IP clauses (general practice; no source fetched; legal review advised): customer retains all IP in uploaded designs; customer warrants they own or are licensed to submit the design and that it infringes no third-party rights; Akrinity receives only a limited, non-exclusive license to use the file solely to quote, prepare and print the order; no reuse, publication, resale, or portfolio/marketing use without written opt-in; access limited to named staff; no disclosure to third parties other than sub-processors (storage provider, payment/shipping); stated retention period and deletion on request; prohibition on printing items that violate law or others' IP (weapons, counterfeit) with the right to refuse; liability cap and a note that print results vary from file quality.
- A short "click-through NDA-style confidentiality" statement is lighter and more practical than a separate signed NDA for a small shop; offer a bespoke mutual NDA only for B2B/prototype customers.
- Watermarking is not useful for the customer's own files (you hold them privately). It applies to showcase models you publish: serve low-poly or decimated GLB previews with an embedded attribution and keep the full-resolution source private, which limits theft of your own designs.
- Retention policy suggestion: auto-delete customer originals N days after order completion (for example 90-180 days) via a scheduled cron job; unconverted quote uploads deleted after 30 days; R2 lifecycle rules can expire objects by prefix automatically (R2 supports lifecycle policies per the multipart doc; expiry rules for completed objects not separately verified). A right-to-delete flow should delete the object and DB metadata, and note backup lifecycles.
- For the international phase, prepare for DPDP (applies May 2027 per sources) now: collect explicit, granular consent at upload (checkbox, unticked by default, versioned notice text, timestamped consent record), keep a record of the sub-processors, enable a withdraw-consent/erase mechanism, and a breach-response procedure with a 72-hour intimation. EU GDPR requirements (lawful basis, transfers, DPA with processors) were not researched here.

### Gaps
- No authoritative source found on standard NDA/IP clauses for 3D-printing services; clause suggestions above are unsourced.
- Primary text of the DPDP Act/Rules (the PIB PDF) was not read; dates and obligations come from law-firm/news summaries that differ by a day on the final commencement date.
- GDPR/EU requirements, cross-border transfer rules under DPDP and any data localization duties were not researched; no source found that confirms R2 `apac` placement satisfies any residency rule.
- Watermarking techniques for 3D models (for example embedding metadata, decimation) were not researched.

## 5. 3D model viewer options (model-viewer, three.js loaders, STEP via occt-import-js, WP plugins, server conversion, validation in the browser) and recommendation

### Takeaway
Use three.js directly, loaded only on pages that need it. It is the only option that can show STL/3MF/OBJ natively, compute bounding box/volume in the browser for customer upload preview, and (lazy-loaded) handle STEP via occt-import-js. Use Google model-viewer only if you want AR and polished GLB showcases; convert showcase models to GLB offline.

### Cited Findings

**Google model-viewer**
- Displays interactive 3D models and AR; AR relies on WebXR (WebXR Device API natively supported, HitTest via polyfill); supports last two major versions of evergreen browsers and last two Safari versions on macOS/iOS; has a separate `<model-viewer-effects>` addon; Apache-2.0; repo tags are glb and gltf; the pages fetched did not list the supported formats or bundle size — [modelviewer.dev](https://modelviewer.dev/); [google/model-viewer GitHub](https://github.com/google/model-viewer)

**three.js loaders**
- `STLLoader` (import `three/addons/loaders/STLLoader.js`): returns a non-indexed `BufferGeometry`; supports binary and ASCII; decodes only the "Magics" binary colour format; assumes little-endian; ASCII assumed UTF-8; `parse(ArrayBuffer)` for in-memory data; ASCII multi-solid files become groups; docs say nothing about units — [three.js STLLoader docs](https://threejs.org/docs/pages/STLLoader.html)
- 3MFLoader and OBJLoader details were not retrievable from the docs (3MFLoader docs URL returned 404; docs index only). General knowledge: 3MF is a ZIP of XML and the loader returns a Group (unverified; see Gaps).
- three.js bundle size: no current figure found. A 2017 measurement of v0.85.2 gave ~504K minified / ~128K gzipped; tree-shaking savings vary (e.g. 773 kB to 590 kB in one real app; 533 kB to 320 kB in another); importing only `Scene` still pulls in much GLSL — [mtmckenna post](https://mtmckenna.github.io/posts/2017/06/18/trying-to-tree-shake-threejs-with-rollup); [three.js forum](https://discourse.threejs.org/t/tree-shaking-three-js/1349/53). These are old, third-party measurements.

**STEP/IGES in browser: occt-import-js**
- Emscripten build of OpenCascade; imports STEP, IGES and BREP via `ReadStepFile`, `ReadIgesFile`, `ReadBrepFile` (Uint8Array input, optional params for `linearUnit` default millimetre, `linearDeflectionType`, `linearDeflection`, `angularDeflection`); returns JSON with node hierarchy and meshes (positions, normals, indices, per-face colours) compatible with three.js; runs in browser or Node, loading a `.wasm` from the same location; LGPL-2.1; `linearUnit` has no effect on BREP; repo shows 135 commits and 26 open issues; npm latest 0.0.23; the WASM size is not stated in the README — [occt-import-js GitHub](https://github.com/kovacsv/occt-import-js); [npm](https://npmjs.com/package/occt-import-js)
- Alternatives surfaced: `occt-js` (@tx-code) is a WASM OCCT 7.9.3 build with B-Rep topology and XDE assembly traversal; `occt-wasm` omits IGES — [occt-wasm GitHub](https://github.com/andymai/occt-wasm); [pkgstats listing](https://www.pkgstats.com/pkg:@tx-code/occt-js) (low-authority aggregators)

**WordPress viewer plugins (existing options)**
- Easy 3D Viewer (`woo-3d-viewer`): STL (binary, ASCII), OBJ (+MTL), glTF in free; 3MF and WRL in PRO; adds a product 3D model box in WooCommerce; one reviewer warns visitors can download uploaded model files — [WordPress.org plugin page](https://wordpress.org/plugins/woo-3d-viewer/)
- 3D Print Showcase supports STL, standard 3MF, GLB, GLTF (no WooCommerce needed); Birlo 3D Print Lite for WooCommerce lets customers upload STL/OBJ/3MF and preview in 3D with material/print settings; "3D Viewer" plugin supports GLB/glTF/OBJ/STL with WooCommerce metabox; 3D Model Viewer by Arty requires a separate platform subscription — [WordPress.org plugin tag/search results](https://es-ar.wordpress.org/plugins/tags/stl/); [3D Viewer plugin](https://wordpress.org/plugins/3d-viewer/) (search-result summary; versions, prices and update dates not verified)

**Server-side conversion**
- `cascadio` (Python, OpenCASCADE) converts STEP to GLB loadable by trimesh; `trimesh` can load STL and export GLB; Blender needs add-ons for accurate STEP import and is awkward headless; STEP has no explicit up-axis (Z-up to Y-up and unit scaling must be handled) and GLB assumes metres while STL is unitless — [cascadio on Socket](https://socket.dev/pypi/package/cascadio/overview/0.0.17); [HF STL2GLB Space](https://huggingface.co/spaces/sanghan/STL2GLB/raw/main/app.py); [convert.guru](https://convert.guru/step-to-glb); [step2glb](https://github.com/vegarringdal/step2glb)

**Volume/bounding box**
- Mesh volume by signed tetrahedra: sum over triangles of scalar triple product / 6; valid only for closed (watertight) meshes; bounding box via `Box3().setFromObject(mesh).getSize()` is in the file's native units; three.js `Mesh.volume()` PR #27906 was questioned by a maintainer and is not settled — [three.js forum on volume](https://discourse.threejs.org/t/volume-of-an-uploaded-stl-file-returning-0-after-calculation/20693); [three.js PR 27906](https://www.github.com/mrdoob/three.js/pull/27906/files/1cd0a447b968e81dd1a9499e3000d84bf665ab4e)

### Inferences
- Comparison for this use case:
  - model-viewer: easiest for polished product pages with AR and lazy loading, but GLB/glTF only (per repo tags; formats not stated in fetched pages), so customer STL/3MF/STEP would need server conversion before preview, and it exposes little geometry access for volume/bounding-box validation. Good as the product-page viewer if showcase models are exported to GLB; mediocre for upload validation.
  - three.js direct: handles STL (STLLoader), 3MF (3MFLoader), OBJ in the browser from a local `File` object (`parse(ArrayBuffer)`) before upload, so the customer gets instant feedback and the page can compute bounding box (mm), triangle count, volume and warn on non-watertight meshes or implausible scale. Heavier bundle (hundreds of KB minified; exact current size unverified) but only needs loading on the upload/product pages, and works via CDN/ES modules without a build step (general knowledge, unverified).
  - Existing WP plugins: fastest to launch for showcase display (Easy 3D Viewer for STL/OBJ/glTF) but 3MF often in paid tiers, WooCommerce-coupled, and plugin vulnerability exposure is the main risk (see Q3); none were verified to provide volume/bounding-box validation, except that Birlo is marketed for customer-upload preview and print-settings.
  - STEP/IGES: occt-import-js is the only no-server browser path found; because the WASM is large (size not confirmed from sources; commonly cited as multiple MB, general knowledge, unverified), load it lazily only when a STEP/IGES file is chosen, or skip the preview for STEP and accept it as "file received, preview unavailable". Server conversion with cascadio/trimesh needs Python and CAD libs, which budget shared hosting typically cannot run; if conversion is wanted, run it on an owner-operated machine (the owner's PC/admin workflow) or a small VPS rather than the web host.
- Recommendation for a solo developer: (1) a small custom three.js module (ES module, lazy-loaded via `wp_enqueue_script_module`, only on product and upload pages) with STLLoader + 3MFLoader + OBJLoader for preview and validation; (2) for product showcase, either the same module with pre-optimized GLB via GLTFLoader or model-viewer if AR matters; (3) STEP/IGES via occt-import-js lazy-loaded on demand, treated as best-effort preview, and always store the original file for the worker; (4) run the validation in the browser for UX only and re-validate server-side (size, structure, triangle count caps), since client-side checks can be bypassed (OWASP principle of server-side validation).
- Mobile: large STL (hundreds of thousands of triangles, 100-300 MB files) can exhaust memory on phones; cap preview size (e.g., skip previews above a threshold) and merge vertices or decimate for display (general knowledge, unverified). A 100 MB binary STL is about 2 million triangles by the 50-bytes-per-triangle format (arithmetic from format layout, unverified here).
- Units: STLLoader docs are silent on units and STL files are unitless; the UI must let the customer confirm mm vs inches, and default assumption should be explicit. occt-import-js defaults output to millimetre for STEP/IGES.
